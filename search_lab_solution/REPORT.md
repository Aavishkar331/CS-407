## Task 0 — Understand the Search Problem

Formulating the warehouse as `P = (S, A, T, s₀, G, c)`:

| Component | Specification |
|-----------|---------------|
| **State `S`** | A cell position `(row, col)` that is not an obstacle. The set of states is every free (`.`, `S`, `G`) cell in the grid. |
| **Actions `A`** | `{Up, Down, Left, Right}` — move one cell in a cardinal direction. |
| **Transition `T`** | `T((r,c), a)` = the neighbouring cell in direction `a`, **provided** that cell is inside the grid and not a `#`. If the target cell is blocked, the action is not available. |
| **Initial state `s₀`** | The cell marked `S` — here `(1, 1)`. |
| **Goal `G`** | The set containing the single cell marked `G` — here `(7, 15)`. |
| **Cost `c`** | Every move has cost `1` (uniform cost). |

**(a) What information is necessary to specify a state?**
Only the cell coordinates `(row, col)`. The robot has no orientation, no load,
and no battery level, so its position completely determines the situation.

**(b) What makes an action invalid?**
An action is invalid when the destination cell is off the grid or is an
obstacle `#`. Such actions are simply never generated by the transition
function.

**(c) Is this a deterministic search problem?**
Yes. Each action leads to exactly one, fully predictable successor state —
there is no randomness or uncertainty in the outcome.

**(d) What would constitute a solution?**
A finite sequence of valid actions (equivalently, a sequence of cells) leading
from `S` to `G`, every step of which is a free cell. An **optimal** solution is
a shortest such sequence (fewest moves, since every move costs 1).

## Task 1 — Plan the Agent (design done *before* prompting any LLM)

1. **State representation:** a Python tuple `(row, col)`. Tuples are immutable
   and hashable, so they can be used as dictionary keys and set members.
2. **Warehouse representation:** a list of equal-length strings (the ASCII
   rows). `grid[r][c]` gives the character at a cell; `#` means blocked.
3. **Valid actions:** generated by `successors(state)`, which tries the four
   cardinal moves and keeps only those whose target cell is free.
4. **Goal recognition:** `is_goal(state)` returns `state == goal_cell`.
5. **Frontier contents:** for A\*, a priority queue of `(f, tiebreak, state)`;
   a `g_score` dict stores the best cost to each state and a `came_from` dict
   stores parent pointers. For BFS, a FIFO queue plus a `visited` set.
6. **Path reconstruction:** follow `came_from` pointers back from the goal to
   the start, then reverse the list.

**What the program reports on termination:** whether a solution was found, the
solution path, the path length (number of moves), and the number of states
expanded. See the `SearchResult` class.

## Task 2 — A\* Implementation

Implemented in `search_agent.py` as `a_star(problem, heuristic)`. Key
components, each mapped to the lab requirements:

- **Represent grid positions as states** — `(row, col)` tuples.
- **Maintain an appropriate frontier** — a `heapq` binary min-heap ordered by
  `f(n)`. A monotonic `counter` breaks ties so states are never compared
  directly.
- **Calculate g, h, f** — `g_score[n]` is the path cost so far; `heuristic(n,
  goal)` is `h(n)`; `f = g + h` is the heap key.
- **Avoid re-expanding states** — a `visited` (closed) set; stale heap entries
  for an already-expanded state are skipped on pop.
- **Reconstruct the path** — `reconstruct_path` via `came_from`.
- **Report path, length, and states expanded** — the `SearchResult` object.

The default heuristic is **Manhattan distance**
`h(n) = |x − x_G| + |y − y_G|`.

## Task 4 — Inspect the A\* Algorithm

| Concept | Where it appears in the code |
|---------|------------------------------|
| **State** | `(row, col)` tuples throughout; `initial_state()` |
| **Action** | the `ACTIONS` list in `WarehouseProblem` |
| **Transition** | `successors()` — yields valid neighbours with step cost 1 |
| **Goal test** | `is_goal()`, checked when a node is popped/expanded |
| **g(n)** | `g_score[state]` dictionary |
| **h(n)** | `heuristic(nxt, goal)` call (`manhattan` by default) |
| **f(n)** | `f_next = tentative_g + heuristic(...)`, the heap key |
| **Frontier** | `frontier`, a `heapq` priority queue |
| **Visited states** | the `visited` closed set |
| **Path reconstruction** | `reconstruct_path()` via `came_from` |

**(a) What data structure is the A\* frontier?** A binary min-heap / priority
queue (`heapq`), ordered by `f(n)`.

**(b) How does the program select the next state to expand?** It pops the heap
entry with the smallest `f(n)` (ties broken by insertion order).

**(c) Where is the heuristic calculated?** In the `heuristic(state, goal)`
function (e.g. `manhattan`), called each time a successor's `f` is computed.

**(d) Does it explicitly compute f = g + h?** Yes:
`f_next = tentative_g + heuristic(nxt, goal)`.

**(e) How is repeated exploration prevented?** Two mechanisms: the `visited`
set stops a state being expanded twice, and the `g_score` check
`tentative_g < g_score.get(nxt, inf)` stops pushing a successor unless a
strictly cheaper path to it has been found.

## Task 5 — A\* vs Blind Search (BFS) on the warehouse map

| Measure | BFS | A\* (Manhattan) |
|---------|-----|-----------------|
| Solution found | yes | yes |
| Path length | 40 | 40 |
| States expanded | 64 | 64 |

**(a) Did both find a solution?** Yes.
**(b) Same path length?** Yes — both 40 (both are optimal for unit costs).
**(c) Which expanded fewer states?** Equal here (64 each).
**(d) Why might A\* expand fewer?** Because its heuristic pulls the search
toward the goal, so it ignores regions that lead away from it, whereas BFS
expands uniformly in all directions.

**Why no difference on *this* map?** The warehouse is essentially one long
winding corridor with 64 reachable free cells and almost no branching. There
are no dead-end side rooms for the heuristic to prune, and the goal sits at the
far end, so *any* correct search must visit nearly every cell. This is itself
the lesson from the sheet: **A\* is not automatically better than blind search —
its advantage depends on the map structure and the heuristic.**

To make the advantage visible, `run_experiments.py` includes two supplementary
maps (see Task 6).

## Task 6 — Investigate the Heuristic

**Why Manhattan distance is appropriate here.** The robot moves only
horizontally and vertically, one cell at a time, at cost 1. On such a
4-connected grid the *minimum possible* number of moves between two cells,
ignoring walls, is exactly `|Δrow| + |Δcol|` — the Manhattan distance. Because
walls can only make the real path *longer*, Manhattan never over-estimates, so
`h(n) ≤ h*(n)`: it is **admissible**, which guarantees A\* returns an optimal
path. It is also *tight* (as large as an admissible heuristic can be for these
moves), so it gives the most guidance.

### Experiment 1 — on the supplied warehouse map

| Heuristic | Solution | Path length | States expanded |
|-----------|----------|-------------|-----------------|
| `h = 0` (uniform cost) | yes | 40 | 64 |
| Euclidean | yes | 40 | 64 |
| Manhattan | yes | 40 | 64 |
| Manhattan × 2 | yes | 40 | 64 |

On the corridor map all four behave identically — again because the single
corridor forces every cell to be expanded regardless of the heuristic.

### Experiment 2 — open-room map (`demo_open_room.txt`)

| Method | Path length | States expanded |
|--------|-------------|-----------------|
| BFS / `h=0` / Euclidean / Manhattan | 12 | 45 |
| Manhattan × 2 | 12 | **13** |

Here the greedy (inadmissible) `2 × Manhattan` expands far fewer states.
Interestingly, plain Manhattan still expands all 45: in an obstacle-free room
the S→G bounding box covers every cell, and each lies on *some* shortest path,
so they all share the optimal `f` and sit on the plateau A\* must clear.

### Experiment 3 — trap map (`demo_heuristic_trap.txt`): admissibility matters

```
########
##..##G#
#....#.#
#.#....#
#S....##
########
```

| Heuristic | Path length | States expanded | Optimal? |
|-----------|-------------|-----------------|----------|
| Manhattan | **8** | 18 | yes |
| Manhattan × 2 | **10** | 13 | **no — 25% longer** |

This is the admissibility lesson concretely: `2 × Manhattan` over-estimates,
so A\* closes a node via a greedy-but-longer route and (having no re-opening of
closed nodes) never corrects it. It finishes faster but returns a **suboptimal**
path.

**Think-About-It — what happens when the heuristic is too optimistic or too
aggressive?**
- *Too optimistic* (`h = 0`): A\* loses all guidance and degenerates to
  uniform-cost search — still optimal, but it expands the most states.
- *Too aggressive* (`h` over-estimates, e.g. ×2): A\* becomes greedy — it
  expands fewer states and runs faster, but it **may lose optimality**, as
  Experiment 3 shows. The guarantee `h(n) ≤ h*(n)` is exactly the line between
  these behaviours.

## Task 7 — Evaluate the LLM-Generated Agent

1. **What was correct immediately?** The overall A\* skeleton — priority queue
   keyed on `f = g + h`, a `came_from` map for reconstruction, and the
   Manhattan heuristic — was conceptually right from the start.
2. **Bugs / design problems found.** The main subtlety is the *closed set*: a
   naive version that re-expands already-visited nodes, or that forgets the
   `g_score` improvement check, either wastes work or can mis-handle costs.
   Tie-breaking also matters — pushing bare `(f, state)` can make Python try to
   compare two tuples, so an explicit counter is needed.
3. **How were they discovered?** By *testing against known answers*, not by
   reading the code alone. Test 4 (alternative paths) and the BFS
   cross-check caught any optimality issue; Test 3 (no solution) confirmed the
   search terminates instead of looping.
4. **Terminology/structures that needed understanding.** `heapq` as a binary
   heap, the distinction between the *open* (frontier) and *closed* (visited)
   sets, and why admissibility guarantees optimality.
5. **Was the code modified?** The design was fixed *before* prompting (Task 1),
   the implementation was written to that design, and tests were added to
   validate it rather than trusting the first output.
6. **Most useful tests.** Test 3 (no solution) and Test 4 (shortest-path
   check) — both target failure modes that "looks-plausible" output hides.
7. **Could the program be trusted without testing?** No. A plausible path is
   not a proof of correctness or optimality.
8. **What was understood about A\* only after implementing it?** That A\*'s
   benefit is *conditional*: on a single-corridor map it offers nothing over
   BFS, and an inadmissible heuristic trades optimality for speed. The
   heuristic and the map structure — not "intelligence" — drive the behaviour.

## Section 6 — Final Reflection

1. **Why formulate the search problem before writing the algorithm?** Because
   the algorithm is only meaningful relative to a precise definition of states,
   actions, transitions, goal, and cost. Without that, you cannot say what a
   "solution" is, what "optimal" means, or even whether your code is correct.
   Formulation turns a vague navigation task into a well-posed problem.

2. **In what sense is A\* "informed"?** It uses extra, problem-specific
   knowledge — the heuristic `h(n)`, an estimate of the remaining cost to the
   goal — to decide where to search next. Blind search (BFS/DFS) uses only the
   structure of the graph explored so far; A\* additionally uses a forecast of
   the future, which lets it prefer states that *look* closer to the goal.

3. **Why does the choice of heuristic matter?** It controls both correctness
   and efficiency. An admissible heuristic (`h ≤ h*`) guarantees optimal paths;
   a tighter admissible heuristic expands fewer states; an inadmissible one can
   be faster but may return a longer path (Experiment 3). `h = 0` is admissible
   but useless as guidance. The heuristic is the knob that trades search effort
   against solution quality.

4. **What did the LLM contribute to the engineering process?** It acted as a
   fast assistant for translating a finished design into idiomatic Python
   (the `heapq`-based frontier, `came_from` reconstruction), accelerating the
   *implementation* step — but not the understanding, specification, or
   validation, which remained the engineer's responsibility.

5. **What could go wrong if LLM code were accepted without testing?** Subtle,
   silent errors: a missing closed-set check (wasted work or wrong costs), a
   bad tie-break (crash or non-determinism), an inadmissible heuristic
   (plausible but suboptimal paths), or no failure handling (infinite loop on
   an unreachable goal). All of these produce *plausible-looking* output while
   being wrong — exactly what systematic testing against known answers catches.

> **Central lesson:** AI Science → AI Engineering.
> Search is the scientific idea; A\* is one algorithm realising it; the LLM is
> an engineering tool that helps implement it. The engineer stays responsible
> for understanding, testing, and validating the resulting system.
